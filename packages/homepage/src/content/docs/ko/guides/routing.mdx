title: 라우팅과 신뢰 프록시

---

Proxer는 공개 요청을 호스트 기준으로 라우팅합니다. 모든 경로가 명시적이기 때문에 서로 다른 클라이언트가 섞이지 않습니다.

---

## 루트 경로와 서브도메인 경로

공개 도메인을 지정해 서버를 실행합니다.

```bash
proxer server --listen 0.0.0.0:8080 --domain proxy.example.com --token dev-token
```

`--subdomain`이 없는 클라이언트는 루트 경로를 등록합니다.

```bash
proxer http 3000 --server wss://proxy.example.com --token dev-token
```

`proxy.example.com` 요청은 이 클라이언트로 전달됩니다.

`--subdomain demo`가 있는 클라이언트는 `demo.proxy.example.com`을 등록합니다.

```bash
proxer http 3000 --server wss://proxy.example.com --subdomain demo --token dev-token
```

알 수 없는 호스트 요청은 `404`를 반환합니다.

`dev-token`은 데모/로컬 테스트용입니다. 실제 배포에서는 긴 난수 토큰을 `PROXER_TOKEN`, Docker/Kubernetes secret, 또는 플랫폼의 secret 메커니즘으로 전달하세요. CLI 인자는 shell history나 process list에 노출될 수 있습니다.

---

## 로컬 테스트

DNS 없이 테스트할 때는 호스트를 직접 지정합니다.

```bash
curl -H 'Host: demo.proxy.example.com' http://127.0.0.1:8080/
```

`localhost`나 IP 기반 요청은 연결된 클라이언트로 자동 라우팅되지 않습니다.

---

## Reverse Proxy 뒤에서 실행하기

Traefik, Caddy, NGINX, 로드 밸런서 같은 reverse proxy 앞단에 Proxer를 둘 때는 그곳에서 TLS를 종료하고 HTTP/WebSocket 트래픽을 loopback 또는 private network를 통해 Proxer로 전달하세요. 원래 Host 헤더도 보존해야 합니다. Traefik에서는 보통 `passHostHeader`를 켜둔 기본 동작을 유지하면 됩니다.

그다음 Proxer에 어떤 프록시 주소의 forwarded 헤더를 신뢰할지 알려줍니다.

```bash
proxer server \
  --listen 0.0.0.0:8080 \
  --domain proxy.example.com \
  --trusted-proxy loopback \
  --trusted-proxy private
```

환경변수는 comma-separated 형식입니다.

```bash
PROXER_TRUSTED_PROXIES=loopback,private,10.42.0.0/16 proxer server --domain proxy.example.com
```

신뢰 프록시는 `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Host`, `X-Forwarded-Proto`를 제공할 수 있습니다. `--trusted-proxy` 또는 `PROXER_TRUSTED_PROXIES`를 설정했다면 reverse proxy는 외부 클라이언트가 보낸 `X-Forwarded-*`와 `X-Real-IP` 헤더를 Proxer로 전달하기 전에 덮어쓰거나 제거해야 합니다. Proxer는 설정된 TCP peer에서 온 이 헤더들을 신뢰하기 때문입니다. 신뢰하지 않는 peer의 forwarded 헤더는 라우팅 판단에 사용하지 않습니다.

## 예약된 내부 경로

모든 Proxer 내부 엔드포인트는 `/__proxer__/` 아래에 있습니다.

```text
/__proxer__/control
/__proxer__/health/live
/__proxer__/health/ready
```

이 경로를 로컬 앱으로 라우팅하지 마세요. 공개 서버가 직접 처리합니다.
