## Prerequisites

- A public machine that can receive HTTP/WebSocket traffic
- A local HTTP service to expose
- Node.js 24 or later if you install from npm

---

## Installation

<Tabs>
  <TabItem label="Windows">

    Download a standalone Windows executable from [GitHub Releases](https://github.com/tinyrack-net/proxer/releases).

    ```powershell
    proxer.exe --version
    ```

  </TabItem>
  <TabItem label="macOS / Linux">

    ```bash
    brew install tinyrack-net/tap/proxer
    ```

  </TabItem>
  <TabItem label="npm">

    npm works on every platform and can be used as a cross-platform fallback.

    ```bash
    npm install -g @tinyrack/proxer
    ```

  </TabItem>
  <TabItem label="Docker">

    ```bash
    docker run --rm tinyrack/proxer --version
    ```

  </TabItem>
</Tabs>

## Starting Fresh

If this is your first time using Proxer, follow these steps to start one public server and expose one local service.

The public `wss://` and `https://` examples below assume TLS is terminated by a reverse proxy or load balancer in front of Proxer, forwarding to Proxer over loopback or a private network.

<Steps>

1. **Start the public server**

   Run Proxer on the machine that receives public traffic.

   ```bash
   proxer server --listen 0.0.0.0:8080 --domain your-server.example.com --token dev-token
   ```

   The server listens for both public requests and tunnel control connections on the same port.

2. **Start a local app**

   On the client machine, start any HTTP service. This example uses Python's built-in server:

   ```bash
   python3 -m http.server 3000 --bind 127.0.0.1
   ```

3. **Connect the root-domain tunnel**

   Omit `--subdomain` to register the root domain route.

   ```bash
   proxer http 3000 \
     --server wss://your-server.example.com \
     --token dev-token
   ```

4. **Test the root route**

   ```bash
   curl https://your-server.example.com/
   ```

5. **Use a subdomain route**

   Start another client with `--subdomain` when you want a named route.

   ```bash
   proxer http 3000 \
     --server wss://your-server.example.com \
     --subdomain demo \
     --token dev-token
   ```

   ```bash
   curl https://demo.your-server.example.com/
   ```

</Steps>

<Aside type="tip">
  For internet-facing deployments, use `wss://` for tunnel clients. Terminate TLS with Caddy, Traefik, NGINX, or a load balancer and forward traffic to Proxer over loopback or a private network.
</Aside>

<Aside type="caution">
  `dev-token` is only for demos and local testing. For real deployments, use a long random token supplied through `PROXER_TOKEN`, Docker/Kubernetes secrets, or your platform's secret mechanism because CLI args can appear in shell history and process lists.
</Aside>

<Aside type="tip">
  During local testing, the `Host` header decides which tunnel receives the request. In production, point your DNS or reverse proxy at the Proxer server and keep the original host header.
</Aside>
